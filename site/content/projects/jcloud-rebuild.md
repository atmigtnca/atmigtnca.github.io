JCloud는 OSLAB이 학생 실습과 연구용 VM을 내주는 OpenStack 클라우드다. 2026년 여름에 이 클라우드를 처음부터 다시 지었다. 새 클라우드를 옆에 세운 뒤 기존 VM, 볼륨, 이미지, 사용자를 옮기고 옛 클라우드를 해체하는 방식이었다.

## 왜 다시 지었나 {#why}

기존 JCloud는 서버에 패키지를 직접 설치하고, 설정 파일을 손으로 고치고, 고가용성은 pacemaker와 DRBD로 묶은 구성이었다. 운영하면서 가장 힘들었던 점은 **설정이 여러 노드와 위치에 흩어져 있어서 무엇이 어디에 있는지 찾기 어렵다**는 것이었다.

7월에 기존 컨트롤 플레인을 실측해 보니 이 문제가 실제 위험으로 이어지고 있었다. 설정은 노드마다 `/etc`, pacemaker 설정, DRBD, 수동 백업 폴더에 나뉘어 있었고, 한쪽 컨트롤러에는 인증서가 없어 장애 조치가 되지 않는 상태였으며, DRBD 복제도 끊겨 있었다. 쓰던 OpenStack Antelope(2023.1)는 이미 upstream 유지보수가 끝나 보안 패치도 나오지 않았다.

그래서 목표를 이렇게 정했다. 컨테이너로 바꾸는 것 자체가 목적이 아니라, **설정을 한곳에 선언해 두고 그 상태로 자동으로 맞춰지게 하는 것**이다. 이후의 모든 선택을 이 기준으로 판단했다.

## 내가 맡은 일 {#role}

**혼자 진행한 재구축이다.** 설계, 구축, 이관, 운영까지 전부 내가 했다.

- **방향과 설계 결정.** 다시 짓기로 한 결정(7월 21일), 스토리지를 전부 Ceph로 모으는 결정(8월 3일), 저장장치 등급 기준(8월 7일), 대시보드 정문(8월 16일)을 정했다. 결정 기록마다 결정한 날짜와 근거를 남겼다.
- **구축과 배포 설정.** 재구축 배포 설정 저장소(JCloud-Deploy)의 2026년 6~9월 커밋 250개 가운데 243개를 내가 작성했다. 나머지 7개는 연구실 공용 계정 커밋이다.
- **이관과 운영.** 기존 VM, 볼륨, 이미지, 사용자를 새 클라우드로 옮기고 옛 클라우드를 해체했다. 지금도 운영을 맡고 있다.
- **검증과 보고.** 교수님 반론을 검증해 비교 보고서를 드렸고, 등급 기준의 근거가 된 fio 실측을 운영 노드에서 진행했다.
- **AI 에이전트를 도구로.** 설계와 판단은 내가 하고, 실측, 배포, 이주의 반복 작업은 AI 코딩 에이전트에게 작업 단위로 맡긴 뒤 결과를 검토해 승인했다. 개인 키나 인증서처럼 사람이 다뤄야 하는 일은 직접 했다.

## 무엇을 비교하고 왜 골랐나 {#choices}

### 배포 방식: Kolla-Ansible {#kolla}

세 가지를 놓고 비교했다.

| 방식 | 내용 | 판단 |
|---|---|---|
| 서버에 직접 설치 + pacemaker/DRBD | 기존 방식 | 문제의 출발점이라 제외 |
| **Kolla-Ansible** | OpenStack 서비스를 컨테이너로 띄우고, 설정은 `globals.yml`과 Ansible 인벤토리에 코드로 둔다 | **채택** |
| OpenStack-on-Kubernetes | 컨트롤 플레인을 쿠버네티스 파드로 운영한다 | 기각 |

처음에는 쿠버네티스 쪽이 더 선언적이라 끌렸다. 지도교수님은 “Kolla로도 배포 편의는 충분하고, 교내 환경에서는 쿠버네티스가 꼭 필요하지 않다”고 반론하셨다. 7월 10일에 이 반론을 반박할 근거가 있는지 일부러 찾아보았는데 결과는 반대였다.

- 대학 연구소 규모에서 Kolla로 여러 번 업그레이드를 끝까지 해낸 사례가 있었다(2018년 사례라 연도를 밝혀 둔다).
- 업그레이드 롤백이 안 되는 것은 Kolla가 아니라 OpenStack 자체의 한계였다. 쿠버네티스로 가도 풀리지 않는다.
- 정전 뒤 데이터베이스 복구도 Galera 기본 기능과 `kolla-ansible mariadb-recovery`로 대응할 수 있었다.
- 우리 규모에서 OpenStack-on-Kubernetes를 실제로 운영한 사례는 찾지 못했고, 쿠버네티스와 OpenStack을 둘 다 운영해야 하는 부담은 upstream도 인정했다.

“쿠버네티스가 운영상 꼭 필요하다”는 주장은 성립하지 않았고, 7월 21일에 Kolla-Ansible로 정했다. 비교 결과는 교수님께 보고서로 드렸다. 8월 6일에 같은 질문을 다시 검토했을 때도 결론은 같았다.

### 업그레이드가 아니라 새로 짓고 옮기기 {#rebuild-not-upgrade}

Antelope에서 Gazpacho까지 정석대로 올라가려면 세 번을 차례로 업그레이드해야 한다. 8월 4일에 경로를 비교한 끝에 **처음부터 Gazpacho(2026.1)와 Ubuntu 24.04로 새 클라우드를 짓고 자원을 골라 옮기는 방식**을 택했다.

- 어차피 모든 VM 디스크를 Ceph 볼륨으로 바꿔 다시 만들어야 해서, 옛 nova 데이터베이스를 그대로 옮겨도 지켜지는 것이 없었다.
- 기존 서버 위에서 세 번 업그레이드하면 문제의 원인인 흩어진 설정 위에서 큰 작업을 세 번 하게 된다.
- 한 번 Kolla 위로 옮겨 두면 다음 해부터는 kolla-ansible이 공식 지원하는 방식으로 업그레이드할 수 있다.

### 스토리지: 전부 Ceph로 {#ceph}

처음 계획은 기존 VM 디스크는 각 서버의 로컬 디스크에 두고 새 VM부터 볼륨 부팅으로 바꾸는 것이었다. 8월 3일에 전체 저장장치와 실제 데이터 양을 전수 실측한 뒤 생각을 바꿨다. **OpenStack 서비스의 시스템 디스크를 빼고 VM 디스크, 볼륨, 이미지를 모두 Ceph에 넣기로** 했다. 용량을 다시 계산해 보니 증설 없이도 들어갔고, 그렇게 해야 VM을 다른 서버로 옮기거나 볼륨에서 부팅하는 경로가 하나로 정리된다.

Ceph 저장장치를 나누는 기준도 따로 정했다. NVMe인지 SATA인지로 나누자는 의견이 있었지만, 이 클러스터에서는 엔터프라이즈 SSD 대부분이 SATA이고 일반 소비자용 SSD 대부분이 NVMe였다. 그래서 인터페이스가 아니라 **등급(엔터프라이즈 SSD, 일반 SSD, HDD)으로 나눴다**. 8월 13일에 fio로 4K 동기 쓰기를 재 보니 엔터프라이즈 SSD가 일반 SSD보다 24배 빨랐고, 확정 응답을 기다리지 않는 쓰기에서는 차이가 1.3배뿐이었다. 차이를 만드는 것이 정전 보호 기능(PLP)이라는 것을 실측으로 확인한 셈이다.

### 대시보드: Skyline을 정문으로 {#skyline}

사용자가 쓰는 웹 대시보드는 Skyline으로 바꿨다. Skyline을 JCloud 색과 한국어 기본 설정으로 꾸며 올린 뒤, 기본 주소로 들어오면 Skyline이 열리게 하고 기존 Horizon은 관리자용 주소로 옮겼다. Horizon을 없애지 않은 것은 Skyline이 아직 지원하지 않는 관리 작업이 있기 때문이다. 주소 분기가 실패해도 기본 백엔드가 Horizon이라 대시보드가 통째로 안 열리는 일은 없게 했다.

## 결과 {#results}

- **새 JCloud.** Ubuntu 24.04 위에 Kolla-Ansible로 OpenStack Gazpacho(2026.1)를 올렸다. 컨트롤러 3대로 구성하고, 스토리지는 cephadm으로 세운 Ceph 19.2.5 Squid를 Kolla에 외부 Ceph로 연결했다.
- **확인한 동작.** 볼륨을 복제해 볼륨 부팅 VM을 만들었고, VM이 ACTIVE가 된 뒤 콘솔 로그인 화면까지 뜨는 것을 확인했다. 이주가 끝난 뒤 옛 클라우드를 해체했고, 지금은 일반 사용자가 새 클라우드를 쓰고 있다.
- **사용자 화면.** 한국어 기본 설정과 JCloud 색을 입힌 Skyline이 대시보드 정문이 됐다.
- **문서.** 방식 비교 보고서, 결정마다 남긴 결정 기록(ADR), 함정과 해결 과정을 적은 운영 노트가 남았다. 설정은 배포 저장소에 코드로 있다.

## 배운 점 {#lessons}

- **실측이 계획을 바꾼다.** 기존 VM 디스크를 로컬에 남기려던 계획은 저장장치 전수 실측 뒤 뒤집혔고, SSD 등급 기준은 fio 실측으로 근거를 얻었다. 문서에 적힌 값보다 직접 잰 값을 먼저 믿게 됐다.
- **명령이 성공해도 결과는 따로 확인한다.** 중앙 로그 수집을 배포했을 때 명령은 성공으로 끝났는데 로그는 한 건도 들어오지 않았다. 로그 수집기 fluentd가 공통 배포 단계에 포함되지 않아 따로 배포해야 했다. 그 뒤로는 종료 코드가 아니라 실제 데이터가 들어왔는지로 완료를 판단한다.
- **설정 변수는 설치된 버전의 예제와 대조한다.** Kolla 변수 이름과 기본값은 버전마다 달라서, 기억이나 블로그 글 대신 설치된 kolla-ansible의 원본 예제를 기준으로 삼았다.
- **사용자는 계정만 옮기면 안 된다.** 사용자, 프로젝트, 역할, 쿼터를 한 묶음으로 옮겨야 새 클라우드에서 바로 쓸 수 있다.

## 한계와 다음 방향 {#next}

- **아직 사람이 하는 일이 남았다.** 모니터링은 배포했지만 보존 기간, 알림 받을 곳 같은 운영 정책은 정하는 중이다. 다음 단계로 모니터링에 AI 에이전트를 붙여 점검 보고를 자동으로 만들고 있다.
- **쿠버네티스는 미뤄 둔 숙제다.** 컨트롤 플레인을 쿠버네티스에 올리는 것은 기각했지만, OpenStack 위에서 쿠버네티스를 서비스로 제공하는 일은 따로 다루기로 했다. 이 계획은 [소개]({{< relref "about" >}}#goal)의 학습 목표로 이어진다.
- **업그레이드는 이제부터다.** 이번에는 새로 지었기 때문에 Kolla의 연례 업그레이드를 아직 한 번도 해 보지 않았다. 다음 릴리스에서 업그레이드 절차를 처음 밟게 된다.
