JCloud는 OSLAB이 학생 실습과 연구용 VM을 내주는 OpenStack 클라우드다. 2026년 여름에 이 클라우드를 처음부터 다시 지었다. 새 클라우드를 옆에 세운 뒤 기존 VM, 볼륨, 이미지, 사용자를 옮기고 옛 클라우드를 해체하는 방식이었다.

## 왜 다시 지었나

기존 JCloud는 서버에 패키지를 직접 설치하고, 설정 파일을 손으로 고치고, 고가용성은 pacemaker와 DRBD로 묶은 구성이었다. 운영하면서 가장 힘들었던 점은 **설정이 여러 노드와 위치에 흩어져 있어서 무엇이 어디에 있는지 찾기 어렵다**는 것이었다.

7월에 기존 컨트롤 플레인을 실측해 보니 이 문제가 실제 위험으로 이어지고 있었다. 설정은 노드마다 `/etc`, pacemaker 설정, DRBD, 수동 백업 폴더에 나뉘어 있었고, 한쪽 컨트롤러에는 인증서가 없어 장애 조치가 되지 않는 상태였으며, DRBD 복제도 끊겨 있었다. 쓰던 OpenStack Antelope(2023.1)는 이미 upstream 유지보수가 끝나 보안 패치도 나오지 않았다.

그래서 목표를 이렇게 정했다. 컨테이너로 바꾸는 것 자체가 목적이 아니라, **설정을 한곳에 선언해 두고 그 상태로 자동으로 맞춰지게 하는 것**이다. 이후의 모든 선택을 이 기준으로 판단했다.

## 무엇을 비교하고 왜 골랐나

### 배포 방식: Kolla-Ansible

세 가지를 놓고 비교했다.

| 방식 | 내용 | 판단 |
|---|---|---|
| 서버에 직접 설치 + pacemaker/DRBD | 기존 방식 | 문제의 출발점이라 제외 |
| **Kolla-Ansible** | OpenStack 서비스를 컨테이너로 띄우고, 설정은 `globals.yml`과 Ansible 인벤토리에 코드로 둔다 | **채택** |
| OpenStack-on-Kubernetes | 컨트롤 플레인을 쿠버네티스 파드로 운영한다 | 기각 |

처음에는 쿠버네티스 쪽이 더 선언적이라 끌렸다. 지도교수님은 "Kolla로도 배포 편의는 충분하고, 교내 환경에서는 쿠버네티스가 꼭 필요하지 않다"고 반론하셨다. 7월 10일에 이 반론을 반박할 근거가 있는지 일부러 찾아보았는데 결과는 반대였다.

- 대학 연구소 규모에서 Kolla로 여러 번 업그레이드를 끝까지 해낸 사례가 있었다(2018년 사례라 연도를 밝혀 둔다).
- 업그레이드 롤백이 안 되는 것은 Kolla가 아니라 OpenStack 자체의 한계였다. 쿠버네티스로 가도 풀리지 않는다.
- 정전 뒤 데이터베이스 복구도 Galera 기본 기능과 `kolla-ansible mariadb-recovery`로 대응할 수 있었다.
- 우리 규모에서 OpenStack-on-Kubernetes를 실제로 운영한 사례는 찾지 못했고, 쿠버네티스와 OpenStack을 둘 다 운영해야 하는 부담은 upstream도 인정했다.

"쿠버네티스가 운영상 꼭 필요하다"는 주장은 성립하지 않았고, 7월 21일에 Kolla-Ansible로 정했다. 비교 결과는 교수님께 보고서로 드렸다. 8월 6일에 같은 질문을 다시 검토했을 때도 결론은 같았다.

### 업그레이드가 아니라 새로 짓고 옮기기

Antelope에서 Gazpacho까지 정석대로 올라가려면 세 번을 차례로 업그레이드해야 한다. 8월 4일에 경로를 비교한 끝에 **처음부터 Gazpacho(2026.1)와 Ubuntu 24.04로 새 클라우드를 짓고 자원을 골라 옮기는 방식**을 택했다.

- 어차피 모든 VM 디스크를 Ceph 볼륨으로 바꿔 다시 만들어야 해서, 옛 nova 데이터베이스를 그대로 옮겨도 지켜지는 것이 없었다.
- 기존 서버 위에서 세 번 업그레이드하면 문제의 원인인 흩어진 설정 위에서 큰 작업을 세 번 하게 된다.
- 한 번 Kolla 위로 옮겨 두면 다음 해부터는 kolla-ansible이 공식 지원하는 방식으로 업그레이드할 수 있다.
